## Core concept already explained

Global instructions and skills are different:

- Global/project context rules are always-on boundaries: how the coding agent
  should behave during every task.
- A skill is an on-demand procedure for a particular job, such as debugging,
  reviewing, preparing a change, or verifying a change.

A simple analogy is: instructions are workplace rules; skills are reusable
playbooks. Hooks automatically react to an event. A workflow coordinates
several playbooks and checks into a larger process. An agent or subagent is a
separate worker with a bounded role and context.

## What currently exists

### Skills

- `verify-change`: selects and runs deterministic project checks and produces
  stable JSON/Markdown evidence.
- `debug-systematically`: requires reproduction, hypotheses, experiments,
  demonstrated root cause, and regression evidence.
- `review-change`: performs a read-only defect review using concrete findings,
  evidence, severity, and confidence.
- `prepare-change`: turns a request and selected repository context into an
  implementation-ready change brief with acceptance criteria and risks.
- `review-security`: acts as an independent, read-only security subagent that
  traces concrete abuse paths and reports findings without replacing scanners.
- `scan-change`: runs project-approved deterministic security scanners while
  suppressing their potentially sensitive output and normalizing pass/fail
  evidence.
- `scripts/gaf.ps1`: installs and synchronizes all canonical skills into Codex
  and Claude user locations and exposes short `verify`, `scan`, and `status`
  commands. This is a tested transitional/local-development installer, not the
  preferred final distribution mechanism.

### Hooks

- `protected-file-guard`: checks intended write paths against a protected-file
  policy without reading secret contents; supports audit-first adoption.
- `fast-feedback`: runs narrow post-edit diagnostics for supported files and
  configured path-scoped commands.

### Workflow

- `workflows/dev-flow`: coordinates preparation, implementation, deterministic
  verification, independent review, remediation, and explicit human gates. It
  includes state and handoff contracts so work can resume.

### Supporting infrastructure

- Provider adapters for Claude and Codex.
- Project configuration schema and examples for .NET/Blazor, React/Vite, and
  Spring/React.
- PowerShell test fixtures covering passing, failing, and missing-tool cases.
- GitHub Actions CI that runs the component tests.
- Safety and architecture documentation.

## Distribution decision and current priority

The user explicitly wants to follow current best practices for creating,
storing, and using skills. Treat `global-agent-flow` as the canonical,
Git-versioned authoring source. Do not put user-created skills under Codex's
`.codex/skills/.system` directory; that location is owned by Codex.

The `gaf` installer is valid for local experimentation but copies a bundle of
skills and requires manual synchronization. Current official guidance prefers
a versioned plugin when distributing multiple reusable skills, hooks, agents,
or connectors. Therefore the likely next engineering direction is:

```text
global-agent-flow (canonical source)
  -> versioned plugin package
  -> provider-supported installation/update mechanism
  -> short skill invocation from any project
```

Do not run `gaf install` or modify global/user configuration before discussing
the plugin approach with the user. The user may retain `gaf verify` and
`gaf scan` as convenience commands even if skill distribution moves to a plugin.

### Reusing other people's components

There are two valid routes:

1. **Install an existing published component.** For Codex, use a trusted plugin
   or the skill installer with a curated skill or GitHub repository path. For
   Claude, install a trusted plugin from a configured marketplace or use its
   supported standalone skill/plugin mechanism. Inspect source, permissions,
   scripts, hooks, network access, licenses, and update behavior before enabling
   it. Prefer a pinned or tagged version when supported.
2. **Reimplement or adapt the pattern.** Do this when the source is unavailable,
   incompatible, untrusted, too broad, or when building it is intentionally part
   of the learning goal. Do not copy copyrighted content or silently claim
   authorship. Preserve attribution and license requirements when adapting code.

The components already in Global Agent Flow were built locally from researched
patterns to teach their design and enforce this repository's safety contracts.
That is not the only way to use community skills. Before building a future
proposal from scratch, search for a maintained authoritative or trusted
existing component, compare fit and permissions, then ask the user whether to
install, adapt, or build.

## Guardrails for future implementation

- Keep reasoning in skills/agents and repeatable enforcement in scripts or
  native CI tools.
- Prefer provider-neutral canonical components with thin provider adapters.
- Validate components manually and with fixtures before attaching automatic
  triggers.
- Start hooks in audit mode when enforcement could block work.
- Never allow an AI reviewer to silently approve its own implementation.
- Keep human approval before sensitive or externally visible actions.
- Do not read, print, commit, or transmit real secrets.
- Do not add production dependencies without explaining the need and obtaining
  approval.
- Run the relevant tests after each implementation and report failures
  honestly.
- Update this handoff or a durable decision log after every accepted or rejected
  proposal so future sessions do not lose the sequence.
